# 운영 플랫폼 설계 — 관리자·팀 권한·콘텐츠 반영·로그

> 목표: 개발팀/디자인팀/운영팀이 각자 웹에서 일하고, 그 결과가 게임에 반영되는 구조.
> 원칙 하나만 지킨다 — **웹이 소유하는 데이터와 게임 서버가 소유하는 데이터를 겹치지 않게 한다.**

## 1. 소유권 (이미 스키마에 반영됨)

| 테이블 | 주인 | 내용 |
|---|---|---|
| `account` | **웹** | 닉·비밀번호·**role** |
| `login_log` | 웹·게임 둘 다 기록(추가만) | 누가 언제 어디서 들어왔나, 실패 포함 |
| `notice` | **웹** | 공지·업데이트 노트 |
| `player` · `inventory` · `room` · `room_item` · `currency_log` | **게임 서버** | 지갑·가방·방·원장 |

추가만 하는 로그 테이블은 두 쪽이 같이 써도 안전하다(같은 행을 고치지 않으므로).

## 2. 권한 (role)

`account.role` 한 컬럼으로 시작한다. 값: `user` · `design` · `dev` · `admin`.

| role | 할 수 있는 일 |
|---|---|
| `user` | 게임 접속만 |
| `design` | 아이템/방 정의 JSON 업로드, 도트 업로드, 미리보기 |
| `dev` | 위 + 서버 설정값(경제 파라미터) 열람·변경 제안, 로그 조회 |
| `admin` | 위 + 공지 발행, 계정 정지, 배포 승인 |

역할을 테이블로 쪼개는 건(`account_role`) 한 사람이 여러 역할을 갖게 될 때 하면 된다. 지금은 한 컬럼이 맞다.

승격은 **DB 에서 직접** 한다(처음 관리자 한 명을 만드는 방법):

```sql
UPDATE account SET role = 'admin' WHERE nick_key = 'doyeon';
```

## 3. 콘텐츠가 게임에 반영되는 길 — 두 갈래를 구분할 것

여기가 이 설계에서 가장 오해하기 쉬운 부분이다. **정의(JSON)와 그림(PNG)은 반영 경로가 다르다.**

| | 어디에 있나 | 바꾸면 |
|---|---|---|
| **아이템/방 정의** (`data/furni/*.json`, `data/rooms/*.json`) | **서버만** 갖고 있다 | 서버만 반영하면 끝. 재시작 또는 핫리로드로 **즉시** |
| **도트 그림** (`client-godot/art/atlas.png`) | **클라이언트**가 갖고 있다 | **클라 업데이트가 나가야** 보인다 |

그래서 디자인팀이 올린 새 가구는 이렇게 흐른다:

```
[웹 관리자 화면]  JSON 업로드 → 검증 → 저장
        │                               ├─ 정의: 게임 서버가 다음 재시작/리로드에 반영  (빠름)
        └─ PNG 업로드 → 격자 복원 →      └─ 아틀라스 빌드 → 클라 새 버전 → 다음 업데이트에 반영 (느림)
```

**검증을 웹에서 해야 하는 이유**: 잘못된 JSON 하나가 서버 기동을 막는다(`DefinitionStore.LoadDir` 는 깨진 파일에서 예외를 던진다).
업로드 시점에 파싱 + 필수 필드 + 좌표/벽 규칙까지 확인하고, 통과한 것만 저장한다. 방 템플릿 규칙은 `docs/room-template-spec.md` 에 정리돼 있다.

### 정의를 어디에 둘 것인가 (택1)

- **A. Git 저장소에 커밋** — 웹이 업로드 받은 JSON 을 저장소에 PR/커밋으로 올리고, 배포 때 반영.
  이력·되돌리기·리뷰가 공짜로 따라온다. "다음 업데이트 때 반영"이라는 요구와 정확히 맞는다. **권장.**
- **B. DB 테이블(`content_def`)에 저장 + 서버 핫리로드** — 관리자가 [적용]을 누르면 즉시 반영.
  빠르지만 이력 관리를 직접 만들어야 하고, 잘못 올리면 라이브가 바로 깨진다.

A 로 시작하고, 나중에 "긴급 수정"이 필요해지면 B 를 얹는 게 안전하다.

## 4. 공지사항

`notice` 테이블(초안/발행 분리). 웹에서 목록·상세를 보여주고, 게임은 접속할 때 **가장 최근 발행 1건**을 받아
기존 `S_Notice`(토스트+채팅 로그)로 띄우면 된다 — 프로토콜을 새로 만들 필요가 없다.

`kind` 로 공지/업데이트/점검을 나눠 두면, 업데이트 노트만 모아 보여주는 페이지를 공짜로 만들 수 있다.

## 5. 접속 로그

`login_log` 에 **웹·게임 양쪽**이 쌓는다(성공·실패 모두). 게임 서버는 게임 루프를 막지 않도록 큐에 넣고 3초마다 함께 쓴다.

관리자 화면에서 볼 것:
- 최근 접속 (닉·시각·web/game·IP)
- 실패가 몰리는 닉/IP — 비밀번호 대입 시도 탐지
- 일별 접속자 수 (`SELECT date(at), count(distinct nick_key) ...`)

> 개인정보 메모: IP 는 개인정보로 취급한다. 보관 기간을 정하고(예: 90일) 지나면 지우는 작업을 나중에 넣는다.

## 6. 어디에 만들 것인가

**화면은 Next.js**, 데이터는 **둘로 나뉜다.**

```
관리자 브라우저
     │  (세션 쿠키 · role 검증)
     ▼
Next.js 서버 라우트  ─┬─▶ Postgres 직접         계정 · 공지 · 로그 (웹이 주인)
                      └─▶ 게임서버 /admin       접속 중인 상태 (메모리에만 있는 것)
```

**브라우저는 게임 서버 관리 API 를 직접 부르지 않는다.** 관리자 토큰이 브라우저로 내려가면 끝이다 —
Supabase `service_role` 키를 안 내려보내는 것과 같은 이유다(CLAUDE.md 최상단 규칙).

### ⚠ 왜 DB 직접 수정으로 끝나지 않는가

`SaveStore` 는 **메모리가 진실**이고 더티 집합을 3초마다 내려쓴다.
접속 중인 사람의 `player.rupee` 나 `inventory` 를 관리자가 DB 에서 고치면 **다음 플러시에 덮어써진다.**
오류도 안 나고 로그도 안 남는다 — "분명 고쳤는데 되돌아가요"로 나타난다.

| 대상 | 접속 중 | 접속 중 아님 |
|---|---|---|
| 계정·역할·공지·로그 | **DB 직접** (웹이 주인) | DB 직접 |
| 지갑·가방·방·외모 | **게임서버 `/admin` 을 거친다** | DB 직접 가능하나, **일관성을 위해 `/admin` 으로 통일** |

## 7. 관리 API 설계

### 7-1. 게임 서버 `/admin/*` — 살아 있는 상태

이미 떠 있는 ASP.NET Core(`WebPort` 8080)에 얹는다. 게임 로직은 건드리지 않고 **읽기와 명령만** 노출한다.

인증: 환경변수 **`HARBOR_ADMIN_TOKEN`** 을 `Authorization: Bearer …` 로 받고 **고정시간 비교**한다.
값이 없으면 `/admin` 전체를 **닫는다**(조용히 열려 있는 것보다 낫다).

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/admin/status` | 접속자 수·방 수·가동 시간·저장 큐 길이 |
| GET | `/admin/online` | 접속 중 목록 (닉·방·접속 시각·IP) |
| GET | `/admin/room?nick=` | 그 사람 방의 가구 배치 (디버깅용) |
| POST | `/admin/broadcast` | 전체 공지 → 기존 `S_Notice` 로 보낸다 (새 opcode 불필요) |
| POST | `/admin/kick` | `{nick, reason}` — 세션 종료 |
| POST | `/admin/grant` | `{nick, rupee?, furniId?, qty?, reason}` — **세션을 통해** 지급 |
| POST | `/admin/reload-defs` | `data/*.json` 다시 읽기 (재시작 없이 아이템·방 반영) |

**`/admin/grant` 가 세션을 거치는 이유**가 이 설계의 핵심이다. `Session.RupeeAdd(delta, reason)` 를 부르면
메모리가 갱신되고 `currency_log` 에 **이유와 함께** 남는다. DB 를 직접 고치면 둘 다 안 된다.
접속 중이 아니면 `SaveStore` 를 통해 같은 경로로 처리한다.

### 7-2. 웹 `/api/admin/*` — 계정·공지·로그

Next.js 서버 라우트. Postgres 를 직접 본다. 매 요청 **세션의 role 을 서버에서 다시 확인**한다
(프론트가 보낸 역할을 믿지 않는다).

| 경로 | 하는 일 | 필요 role |
|---|---|---|
| `GET /api/admin/accounts` | 검색·목록 (해시는 절대 안 내보낸다) | `admin` |
| `POST /api/admin/accounts/role` | 역할 변경 | `admin` |
| `POST /api/admin/accounts/ban` | 정지 (`account.banned`) | `admin` |
| `GET /api/admin/logins` | 접속 로그·실패 몰림 | `dev` 이상 |
| `GET /api/admin/currency` | 루피 원장 (`currency_log`) | `dev` 이상 |
| `CRUD /api/admin/notices` | 공지 작성·발행 | `admin` |

### 7-3. 감사 로그

**관리자 행위는 전부 남긴다.** `admin_log(actor, action, target, detail, at)` 테이블을 추가한다.
지급·정지·킥처럼 되돌리기 어려운 일이 누가·언제·왜 일어났는지 없으면 나중에 아무것도 못 따진다.
(스키마를 추가하면 `Db.AddMissingColumns` 규칙도 같이 지킬 것.)

### 7-4. 보안 점검 (공개 전)

- `/admin` 은 토큰 없으면 **전면 거부**. 토큰은 `.env` 에만, 브라우저로 내려보내지 않는다.
- 웹 관리자 라우트는 **매 요청 role 재검증**. 화면을 숨기는 것은 방어가 아니다.
- 관리자 로그인에도 **속도 제한**을 건다(일반 로그인과 같은 문제).
- 상세 오류를 관리자 화면 밖으로 내보내지 않는다.

## 8. 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | Postgres 이전 + 소유권 분리 + `role`·`login_log`·`notice` 테이블 | **완료** |
| 2 | 입장권 HMAC 서명 → 웹을 어디로든 떼어낼 수 있게 | **완료** (16차) |
| 3 | **게임서버 `/admin` API** — status·online·broadcast·kick·grant·reload | 다음 |
| 4 | Next.js 관리자 화면: 로그인, 접속 로그, 공지 작성/발행 | |
| 5 | 정의(JSON) 업로드 + 검증 + Git 커밋 파이프라인 | |
| 6 | 도트 업로드 → 아틀라스 빌드 → 클라 버전 발행 | |
| 7 | 클라 버전 체크 + 업데이트 안내 화면 | |

단계 3을 먼저 하는 이유: **화면 없이도 쓸모가 있다.** `curl` 로 공지·킥·지급이 되면 그 자체가 운영 도구고,
나중에 Next.js 화면은 이 API 를 부르기만 하면 된다. 화면부터 만들면 붙일 게 없다.
