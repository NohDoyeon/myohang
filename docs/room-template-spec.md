# 방 템플릿 규격 (다른 AI에게 그대로 붙여 넣는 브리프)

> 묘항(Myohang)의 방은 `data/rooms/<roomId>.json` 한 장이 곧 한 방이다.
> 아래 규칙은 **서버 코드가 실제로 강제하거나(벽 판정·걷기), 어기면 조용히 망가지는 것**(넓히기 포함 관계)들이다.
> 규칙을 어긴 방은 서버가 버리지 않고 **경고 후 보정**하므로, 티가 안 나게 가구 자리만 틀어진다. 그래서 규칙이 곧 검수 기준이다.

---

## 붙여 넣을 프롬프트 (여기부터 복사)

당신은 아이소메트릭(2:1) 커뮤니티 게임의 방 레이아웃을 만든다. 출력은 **JSON 파일 내용만**.

### 1. 파일 형식

```json
{
  "roomId": "cabin_wide_02",
  "name": "넓은 다락방",
  "kind": "private",
  "heightmap": [
    "xxxxxxxxxxxxxxxx",
    "x00000000000000x",
    "x00001110000000x",
    "x00001110000000x",
    "x00000000000000x",
    "xxxxxxxx00xxxxxx"
  ],
  "door":  { "x": 8, "y": 5, "dir": 0 },
  "wall":  { "style": "wall_wood_01", "height": 3 },
  "floor": { "style": "floor_carpet_blue" },
  "spawn": [ { "x": 8, "y": 4, "dir": 4 } ],
  "maxUsers": 30,
  "upgrade": "cabin_grand_03",
  "upgradePrice": 2500
}
```

### 2. heightmap — 방의 전부

- 문자열 배열. **모든 행의 길이가 같아야 한다** (다르면 서버가 기동 중 예외).
- `x` = 방 바깥(못 걷고, 렌더도 안 된다). `0`~`9` = 바닥 높이 0~9. `a`~`z` = 10~35.
- 좌표는 `x` = 행 안의 인덱스(열), `y` = 행 번호. 화면에서 **+x 는 오른쪽 아래, +y 는 왼쪽 아래**로 간다. 즉 **배열의 왼쪽 위가 화면의 가장 안쪽(뒤)**이다.
- **바깥 테두리는 전부 `x`** 로 감싼다(문 칸만 예외, 아래 참고).
- 높이는 **0 과 1 만** 쓴다. 2 이상은 받침(riser)이 너무 높아 어색하다. 한 단 높은 구역(단상)은 **직사각형**으로.

### 3. 벽 — 뒤쪽 두 면에만 자동으로 생긴다

벽은 JSON 에 적는 게 아니라 heightmap 에서 계산된다:

- **서쪽 벽**(타일의 왼쪽 위 모서리): `(x' ≤ x-1, y' ≤ y)` 영역에 걸을 수 있는 칸이 **하나도 없을 때** 생긴다.
- **북쪽 벽**(타일의 오른쪽 위 모서리): `(x' ≤ x, y' ≤ y-1)` 영역에 걸을 수 있는 칸이 **하나도 없을 때** 생긴다.
- 즉 **왼쪽 끝 열과 위쪽 끝 행에만 벽이 생긴다.** 앞으로 튀어나온 칸(문 등)에는 벽이 생기지 않는다(뒤 칸을 가리게 되므로).
- ㄱ자처럼 꺾인 방을 만들면 **오목한 안쪽 모서리에는 벽이 생기지 않는다.** 그 자리는 "뻥 뚫린 것처럼" 보이므로, 꺾는 방향은 **오른쪽 아래 방향으로만**(왼쪽 위 윤곽은 직선으로 유지) 잡는 것이 안전하다.
- 벽걸이 가구(포스트잇·창문·시계)는 벽이 있는 칸에만 붙는다. 벽 한 칸은 가로 2칸 × 세로 `wall.height` 칸의 슬롯으로 나뉜다.

### 4. 문과 스폰

- `door` 는 **걸을 수 있는 칸**이어야 한다. 관례상 **아래쪽 테두리에서 한 칸 튀어나오게** 뚫는다(그 행은 그 칸만 `0`, 나머지는 `x`).
- `spawn[0]` 이 입장 위치. **걸을 수 있는 칸**이어야 하고, 보통 문 바로 안쪽. `dir` 4 = 정면(화면 아래쪽)을 본다. 0/2/4/6 중에서 고른다.

### 5. 넓히기 체인 — 이것을 어기면 가구가 어긋난다

`upgrade` 는 "이 방을 넓히면 되는 다음 템플릿", `upgradePrice` 는 그 값(루피). 마지막 단계는 `upgrade` 를 생략한다.

**다음 단계는 이전 단계를 같은 좌표로 품어야 한다:**

1. 이전 단계에서 걸을 수 있던 칸은 **전부 같은 (x,y) 에서 걸을 수 있어야** 한다.
2. 그 칸들의 **높이 문자가 같아야** 한다 (단상은 같은 자리에 같은 모양으로).
3. 이전 단계에서 **벽이 있던 칸은 새 단계에서도 벽이 있어야** 한다 → 실질적으로 **왼쪽 위 테두리(`x=1` 열, `y=1` 행)를 그대로 두고, 오른쪽과 아래로만 넓힌다.**
4. 이전 단계의 문 칸은 새 단계에서 평범한 바닥이 된다(문은 더 아래로 내려간다). 그래도 걸을 수 있어야 한다.

넓히면 방의 가구는 좌표 그대로 따라온다. 위 규칙이 깨지면 가구가 못 걷는 칸에 갇히거나 벽걸이가 엉뚱한 자리로 밀린다.

### 6. 크기 상한

기본 줌이 2배라 **걸을 수 있는 영역이 24×14 칸을 넘으면 한 화면에 안 들어온다.** 마지막 단계도 그 안에서 끝낸다.

### 7. 나머지 필드

- `kind`: 개인 방은 `"private"`, 공용 방은 `"public"`.
- `wall.style`: 문자열에 `wood` 가 들어가면 나무색, `rail` 이면 푸른 난간색, 그 외는 회보라. `wall.height` 는 3(실내) 또는 1(실외 난간).
- `floor.style`: 지금은 표시용(클라가 아직 안 쓴다). 이름만 의미 있게.
- `maxUsers`: 개인 방 25~40, 공용 방 60.
- `furni`(선택): 저장본이 없을 때만 놓이는 기본 가구.
  `[{ "furniId": "lamp_floor", "x": 2, "y": 2, "dir": 2, "wallU": 0, "wallV": 0, "tilt": 0 }]`
  바닥 가구는 걸을 수 있는 칸에, 벽걸이는 **실제로 벽이 있는 칸**에 `dir` 4(북쪽 벽) 또는 2(서쪽 벽), `wallU` 0~1, `wallV` 0~(wall.height-1).
  쓸 수 있는 furniId: `chair_wood` `table_round` `rug_round` `plant_pot` `flower_pot` `lamp_floor` `tv_crt` `bookshelf` `fridge_red` `cola_machine` / 벽: `window_round` `frame_photo` `clock_wall` `aircon_wall` `postit_yellow`.

### 8. 자가 검사 (출력 전에 직접 확인할 것)

- [ ] 모든 행의 길이가 같은가?
- [ ] 바깥이 `x` 로 닫혀 있는가? (문 칸 제외)
- [ ] 문·스폰이 걸을 수 있는 칸인가? 문이 아래로 튀어나와 있는가?
- [ ] 걸을 수 있는 칸이 **하나로 이어져** 있는가? (길이 끊기면 못 가는 구역이 생긴다)
- [ ] 이전 단계의 모든 걸을 수 있는 칸이 같은 좌표·같은 문자로 남아 있는가?
- [ ] `x=1` 열과 `y=1` 행을 건드리지 않았는가?
- [ ] 걸을 수 있는 영역이 24×14 이내인가?
- [ ] 단상이 직사각형이고 높이가 1인가?

(여기까지 복사)

### 화면에 들어오는 크기 (이게 진짜 상한)

타일은 64×32, 뷰포트는 1280×720, 줌은 1·2·3·4배(기본 2배)뿐이라 **줌 1배가 가장 넓게 보는 상태**다.

## ㄱ자 방을 만들 때 (실제로 걸린 함정)

벽은 **누적 영역**으로 판정한다. `North(x,y)` 는 `(x' ≤ x, y' ≤ y-1)` 사각형 **전체**가 비어 있을 때만 생긴다.
따라서 ㄱ자 방은 홈을 **먼 구석(x 작고 y 작은 쪽)** 에만 팔 수 있다.

```
✅ 먼 구석을 도려냄 — 도려낸 면에 벽이 생긴다     ❌ 오른쪽 아래에 날개를 붙임 — 날개 윗변에 벽이 없다
   xxxxxxxxxxxx                                    xxxxxxxxxxxx
   xxxx0000000x   ← 이 줄 윗변에 북쪽 벽 ✓          x000000xxxxx
   xxxx0000000x                                    x000000xxxxx
   x0000000000x   ← x1~3 윗변에도 북쪽 벽 ✓         x0000000000x   ← x7~10 윗변에 벽이 안 생김
   x0000000000x                                    x0000000000x      (왼쪽 위에 바닥이 남아 있어서)
```

`RoomUpgradeTests.BackEdges_HaveWalls` 가 이걸 자동으로 잡는다 — "위/왼쪽이 비었는데 벽이 없는 칸"을 찾아낸다(문 칸만 예외).

## 계열(집 모양)을 늘릴 때

넓히기는 **같은 계열 안에서만** 올라간다(포함 관계 때문에). 계열을 바꾸는 것은 **이사**(`C_RemodelRoom`)다.

새 계열을 추가하면 자동으로 이사 목록에 뜬다 — 필요한 건 JSON 의 두 줄뿐이다:

```json
"family": "corner",   // 계열 id. 같은 계열끼리만 넓히기로 이어진다
"tier": 2             // 계열 안의 단계(1부터). 이사할 때 같은 단계를 찾는 기준
```

- 이사 목록은 **계열마다 한 채**, 지금 살고 있는 단계와 **같은 단계**를 보여준다(그 계열에 그 단계가 없으면 마지막 단계).
  넓히는 데 쓴 루피가 이사 한 번에 날아가지 않게 하기 위함이다.
- 이사하면 **놓여 있던 가구가 전부 주인 가방으로 돌아온다**(모양이 달라 제자리에 둘 수 없다). 포스트잇 본문은 사라진다 — 떼는 것과 같다.
- 값은 `Economy.RemodelPrice`(기본 1,000). **계열 간 단계 값 차이보다 비싸야 한다** — 싸면 싼 계열로 올린 뒤 비싼 계열로 이사해 이득을 본다.
  지금 3단계까지 드는 값: 다락방 3,300 / 모퉁이집 3,700 / 복층방 4,000 → 차이 700 < 이사비 1,000 ✓
- 서버는 클라가 보낸 `templateId` 의 **계열만** 쓰고 단계는 다시 고른다(높은 단계를 요청해도 통하지 않는다).
- 기동할 때 `Program.cs` 가 사슬을 훑어 `family`/`tier` 가 비었거나 `upgrade` 가 이어지지 않으면 `⚠` 로 알린다.
