# 웹 클라이언트 이전 계획 — Godot → Next.js(React) + TypeScript

> 결정 (2026-09-21): **웹으로 간다.** Godot 클라이언트는 웹 클라이언트가 따라잡은 뒤 정리한다.
> 이 문서는 "무엇이 남고, 무엇을 다시 쓰고, 어떤 순서로 가는가"를 정한다.

## 0. 왜 웹인가

우리가 재현하려는 2000년대 게임들(퍼피레드·팝플·싸이월드 미니룸, 그리고 원조 Habbo)은 전부
**브라우저 안에서 Flash 로** 돌았다. 웹에서 로그인하면 같은 페이지에 게임 화면이 떴고, 받을 것이 없었다.
그 접근성이 이 장르의 핵심이었다.

Flash 는 2020년에 끝났다. 지금 그 자리를 대신하는 것은 **Canvas/WebGL(HTML5)** 이다.
즉 "웹에서 로그인하면 바로 게임창"을 지금 만들려면 JS/TS + WebGL 이 유일한 현대판 경로다.

덧붙여 **exe 배포 자체가 마찰**이다. 오늘(9/18) 확인한 것만 해도 70MB zip, 압축 해제 위치,
`harbor://` 등록, SmartScreen 경고, dll 누락 가능성이 전부 테스터가 넘어야 할 턱이었다.
웹이면 링크 하나로 끝난다.

## 1. 무엇이 남고 무엇이 사라지는가

경계가 이미 깨끗하다. **게임 규칙·경제·데이터는 전부 서버에 있고, 클라이언트는 그리기와 입력만 한다.**

| | 줄 수 | 운명 |
|---|---|---|
| `Harbor.Server` + `Harbor.Core` + `Harbor.Protocol` | 2,905줄 / 33파일 | **거의 그대로 남는다** |
| `client-godot/scripts` | 3,210줄 / 12파일 | **전부 다시 쓴다** |

### 그대로 재사용되는 것

- **DB 전체** — 계정·플레이어·인벤토리·방·방아이템·원장. 아이템은 클라이언트가 아니라 DB 에 있다.
- **방 템플릿** `data/rooms/*.json` — 좌표계가 같으므로 손댈 것이 없다.
- **아트** `art/atlas.png` + `atlas.json` — PixiJS 가 그대로 읽는다. 아틀라스 파이프라인(`tools/build-avatar-atlas.py`)도 유지.
- **웹 로그인·서명 입장권** — 이미 게임 서버와 분리돼 있다. `t1.` 입장권을 그대로 쓴다.
- **프로토콜 정의** `Packets.cs` (168줄) → TypeScript 타입으로 옮긴다. 기계적인 작업이다.

### 다시 쓸 것의 실제 덩어리

```
RoomView.cs    851줄   방 렌더링 · 입력 · 카메라
HudView.cs     656줄   UI 전체 (채팅·인벤토리·상점·설정)
FurniSprite.cs 458줄   가구 그리기
AvatarView.cs  434줄   캐릭터 애니메이션 · 팔레트 스왑
                     ─────
                    2,399줄   ← 일의 대부분이 여기 있다
```

나머지(`AssetCatalog` 77, `NetClient` 92, `Ui` 152, `SpritePalette` 87 …)는 작다.

### 통째로 사라지는 것

- **`HangulInput.cs` (237줄)** — 브라우저는 IME 를 네이티브로 처리한다.
  CLAUDE.md 의 "`LineEdit`/`TextEdit` 금지" 규칙도 같이 사라진다.
- **내보내기 파이프라인 전부** — `HarborClient.sln`, `export_presets.cfg`, `pack-client.sh`,
  `tools/client/*`, 그리고 `atlas.json` 이 pck 에 들어갔다 말았다 하던 문제(WORKLOG 17차).
- **`tools/import-assets.ps1`** — Godot 의 임포트 개념이 없어진다.

## 2. 기술 선택

```
Next.js 페이지 ─┬─ <canvas>   PixiJS (WebGL) — 아이소메트릭 월드, 게임 루프
                └─ React      채팅창 · 인벤토리 · 상점 · 설정 · 모달
```

| 층 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js + TypeScript** | 랜딩·로그인이 이미 Vercel 에 있다. 같은 프로젝트로 합쳐진다 |
| 월드 렌더링 | **PixiJS** | 스프라이트 대량 배치에 맞고, 커스텀 필터로 팔레트 스왑을 옮길 수 있다 |
| 직렬화 | **@msgpack/msgpack** | 서버의 MessagePack 과 그대로 맞는다 |
| 전송 | **WebSocket (wss)** | 브라우저는 raw TCP 를 못 연다 |

### ⚠ 설계 함정: React 로 월드를 그리지 않는다

타일 하나를 React 컴포넌트 하나로 만들면 프레임이 안 나온다.
**캔버스 안쪽은 Pixi 의 게임 루프가 명령형으로 그리고, React 는 화면 주변부만 맡는다.**
둘 사이는 상태 저장소(zustand 등) 하나로 잇는다 — 서버 스냅샷이 들어오면 저장소를 갱신하고,
Pixi 는 저장소를 읽어 그리고, React 는 구독해 다시 그린다.

## 3. 서버에 추가할 것

### WebSocket 엔드포인트

서버는 이미 ASP.NET Core 를 8080 에 띄우고 있다(`Program.cs:56`, `UseUrls("http://0.0.0.0:8080")`).
거기에 `app.UseWebSockets()` 와 엔드포인트 하나를 더해 기존 `Session`/`Dispatcher` 에 연결한다.

**프레임 형식은 바꾸지 않는다.** 현재 형식은:

```
[uint32 length][uint16 opcode][MessagePack body]     (리틀엔디언, Framing.cs)
length = opcode(2) + body 바이트 수
```

WebSocket 은 이미 메시지 경계를 주므로 `length` 4바이트는 사실 남는다. 그래도 **그대로 둔다** —
`Framing.Encode` 를 손대지 않아도 되고, TS 쪽 디코더도 같은 규칙 하나만 구현하면 된다.
4바이트를 아끼자고 서버·클라 양쪽에 분기를 만들 이유가 없다.

바이너리 메시지 하나 = 프레임 하나로 보낸다. 규모: **100~150줄** 수준.

### TLS (`wss://`) — 인증서는 **앞단**이 든다

**선택이 아니라 강제다.** HTTPS 페이지에서 브라우저는 `ws://` 를 거부한다.

다만 **게임 서버는 TLS 를 몰라도 된다.** 표준 구조는 앞에 리버스 프록시를 두는 것이다:

```
브라우저 ──wss(TLS)──▶ 리버스 프록시 ──ws(평문)──▶ Harbor.Server :8080
                        ↑ 인증서는 여기               ↑ 얘는 그대로 둔다
```

인증서는 90일마다 갱신해야 하고 갱신 실패는 전면 장애다. 그걸 게임 서버에 얹으면 게임을 배포할 때마다
인증서가 딸려온다. **그래서 `/ws` 엔드포인트는 앞으로도 평문 `ws` 만 말한다.**

**선택 (2026-09-21): 개인·소규모로 간다. 클라우드는 나중.**

| 단계 | 방식 | 인증서 |
|---|---|---|
| **지금** | **Cloudflare Tunnel** — `cloudflared tunnel --url http://localhost:8080` | Cloudflare 것, 갱신 불필요 |
| 도메인이 생기면 | Caddy — `game.example.com { reverse_proxy localhost:8080 }` | Let's Encrypt 자동 |
| 사람이 늘면 | Fly.io / Railway 등에 .NET 8 컨테이너 | 플랫폼 제공 |

Cloudflare Tunnel 을 고른 이유: 공유기를 안 만지고, 테스터는 아무것도 설치하지 않고, **랜딩·API·WebSocket 이 주소 하나로 합쳐진다.**
(`docs/deploy-mvp.md` 에 "Cloudflare Tunnel 은 TCP 30000 에 부적합"이라 적어 둔 것은 **raw TCP 얘기**였다.
WebSocket 은 HTTPS 위에서 도니 해당 없다 — 웹으로 옮기면서 사라진 제약이다.)

무료 `trycloudflare.com` 주소는 **실행할 때마다 바뀐다.** 고정하려면 계정 + 도메인이 필요하다.

### 배포 절차 (2026-09-21 기준)

```
브라우저 ──https──▶ Vercel (webapp: 랜딩·로그인·게임·관리자)
         ──wss────▶ Cloudflare Tunnel ──▶ 내 PC :8080/ws
```

**비밀번호는 게임 서버로 가지 않는다.** 웹이 Postgres 로 확인하고 **입장권만** 넘긴다
(`webapp/app/api/login/route.ts` → sessionStorage → `/play` 가 `C_Login` 으로 제출).
입장권을 URL 에 싣지 않는 이유는 서버 로그·브라우저 히스토리·`Referer` 에 남기 때문이다.

1. **터널 열기** — `cloudflared tunnel --url http://localhost:8080`
   → `https://<무작위>.trycloudflare.com` 을 준다. **실행할 때마다 주소가 바뀐다**(고정하려면 계정+도메인).
   ⚠ 이 터널은 `:8080` 전체를 연다 — `/admin` 도 함께 공개된다. 토큰이 있어야 통과하지만 **테스트가 끝나면 끈다.**
2. **Vercel 설정** — Settings → General → **Root Directory 를 `landing` → `webapp`**
3. **환경변수** (Settings → Environment Variables), 견본은 `webapp/.env.example`
   - `NEXT_PUBLIC_GAME_WS` = `wss://<터널주소>/ws`
   - `HARBOR_DB` · `HARBOR_TICKET_SECRET` (게임 서버 `.env` 와 **같은 값**)
   - **값을 바꾸면 반드시 Redeploy** — Vercel 은 배포 시점에 주입한다(16차에서 여기서 막혔다)
4. **게임 서버를 켜 둔다** — `bash tools/run-server.sh`. PC 를 끄면 게임도 꺼진다.
5. 다른 PC 에서 접속 확인.

`landing/` 은 2번이 끝날 때까지 지우지 않는다 — 지금 실제로 서비스 중인 페이지다.

### 나중에 클라우드로 옮길 때를 위해 지금 지킬 것

확장성을 위해 필요한 건 사실상 **주소를 코드에 박지 않는 것 하나**다.

- 서버 주소·포트는 **환경변수/설정으로만** (`HARBOR_DB`, `Server:WebPort` …). 소스에 상수로 넣지 않는다.
- 웹 클라이언트도 WebSocket 주소를 **빌드 타임 설정**에서 받는다. `ws://localhost:8080/ws` 를 코드에 쓰지 않는다.
- 서버는 이미 상태를 **Postgres 에 둔다**(파일 아님) → 컨테이너로 옮겨도 그대로 뜬다.
- TLS 를 서버에 넣지 않는 것 자체가 이식성이다. 앞단만 갈아끼우면 된다.

그리고 이것이 지금의 보안 숙제를 같이 해결한다. 현재 게임 연결은 평문이다
(`Session.cs:142` 가 `NetworkStream` 을 그대로 쓴다) — 채팅·닉네임은 물론
`C_Login.Token` 에 담기는 **비밀번호까지 평문으로 흐른다**(`Packets.cs:123`).
터널이든 포트포워딩이든 이건 해결되지 않는다. **웹 이전과 보안 수정이 같은 작업이 된다.**

남은 평문 관련 부채:
- 입장권은 만료(5분) 전까지 **재사용 가능**하다(`TicketStore.cs:16`). 같은 닉 동시 접속만 막힌다.
- **로그인 시도 횟수 제한이 없다.** 공개 운영 전에 반드시 붙인다.
- 공개 기간에는 `Server:AllowGameSignup` 을 **false** 로 둔다(가입은 웹에서만).

## 4. 단계별 계획

**한 번에 갈아엎지 않는다.** 각 단계가 끝날 때마다 **돌아가는 게임이 하나는 있어야 한다.**
프로토콜이 계약서라서 Godot 클라와 웹 클라가 공존할 수 있다.

| 단계 | 하는 일 | 끝났다고 보는 기준 |
|---|---|---|
| **0** | WebSocket 엔드포인트 + `wss` | Godot 클라는 TCP 로 **그대로 동작**. 브라우저 콘솔에서 `C_Ping` → `S_Pong` 왕복 |
| **1** | TS 프로토콜 · 접속 · 로그인 | 웹에서 입장권으로 로그인 → `S_RoomSnapshot` 을 **콘솔에 찍기**까지 |
| **2** | 방 그리기 (Pixi) | 바닥·벽·가구가 제자리에. 아직 못 움직여도 된다 |
| **3** | 이동 · 캐릭터 | 클릭 이동, 다른 사람 보이기, 애니메이션 |
| **4** | 채팅 · UI 뼈대 (React) | 말풍선, 채팅창. 한글 입력이 **그냥 된다**는 것 확인 |
| **5** | 인벤토리 · 가구 놓기 · 상점 | 경제 한 바퀴가 웹에서 돈다 |
| **6** | 나머지 (화분·포스트잇·출석·복권·방 넓히기) | 기능 동등 |
| **7** | **Godot 클라 정리** | `client-godot/` 와 내보내기 도구 일체 제거 |

단계 0~1 이 가장 중요하다. 여기가 뚫리면 나머지는 그리기 작업이다.

## 5. 옮길 때 반드시 지킬 불변식

클라이언트를 다시 쓰면서 **조용히 깨지기 쉬운** 것들이다. CLAUDE.md 와 중복되지만 여기 다시 적는다.

- **아이소메트릭 투영은 2:1** — `Iso.TileW=64, TileH=32` (`Harbor.Core/Iso.cs`, 30줄). 그대로 옮긴다.
- **벽 규칙은 누적 접두(cumulative prefix)** — `Walls.West/North` (33줄). 직관적으로 다시 쓰면 틀린다.
- **`S_InventoryUpdate.Qty` 는 델타가 아니라 현재 보유 수량(절대값)**.
- **방 저장 키는 `u:{닉}`** — 템플릿과 무관하다.
- **상점 카탈로그는 `price.amount > 0` 만 내보낸다** (0 = 수확물 = 파는 물건).
- **그리기 순서(depth)** 는 아이소메트릭에서 직접 계산해야 한다. Pixi 의 `zIndex` 를 쓰되 기준은 타일 좌표다.

`Harbor.Core` 의 순수 로직 중 클라이언트에 필요한 것(`Iso` 30, `Heightmap` 36, `Walls` 33)은
**합쳐서 100줄 남짓**이다. TS 로 다시 쓰는 편이 빠르고, 서버와 값이 어긋나지 않는지 테스트로 묶는다.

## 6. 미지수 · 위험

- **팔레트 스왑을 Pixi 필터로 옮기는 것** — 정확 색상 일치 방식은 그대로 되지만 실제로 해봐야 안다.
  현재 `palette_swap.gdshader` 는 톨러런스 0.02, 최대 16쌍이다.
- **동시 인원과 트래픽** — 방 하나는 사람 수의 제곱으로 트래픽이 는다. 광장 정원 60은 아직 검증 안 됐다.
  WebSocket 으로 바뀌어도 이 성질은 같다.
- **모바일** — 웹이 되면 자연히 폰에서도 열린다. 하지만 **터치 입력과 화면 크기는 별도 설계**다.
  이번 이전 범위에 넣지 않는다.
- **에셋 용량** — 지금은 아틀라스 한 장이라 가볍지만, 가구·방이 늘면 로딩 전략이 필요해진다.

## 7. 그때까지 Godot 클라는

**지운다고 결정했지만, 단계 7 전에는 지우지 않는다.** 이유:

1. 웹 클라가 못 따라온 기능을 **여전히 쓸 수 있다**.
2. 새 렌더링이 맞는지 **비교 대상**이 된다 — "Godot 에선 이렇게 보인다"가 정답지 역할을 한다.
3. 서버 변경이 프로토콜을 깨뜨리면 **두 클라 모두에서** 티가 난다.

대신 **Godot 클라에 새 기능을 넣지 않는다.** 지금부터 들어가는 클라 기능은 웹 쪽에만 쌓는다.
